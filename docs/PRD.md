# 耐用品价值管理微信小程序 PRD

版本：1.3

更新日期：2026-10-24

状态：按当前实现及用户确认更新；上线验收与未决政策见第 13 节

产品名称：当前界面使用「用本」，正式对外名称待确认

本文用于明确首版产品范围、功能、业务规则、异常处理和验收标准。本版以当前实现及用户最新确认作为产品基线：记录物品生命周期，不要求操作审计；按状态查询，不提供处置日期区间筛选；凭证在物品编辑中统一管理。已实现能力不等于已完成真机或上线验收，未决政策与验收项另列。本文不包含前端样式、视觉规范或技术实现方案。

## 1. 产品定义

### 1.1 产品定位

产品是一款运行在微信内的耐用品价值管理小程序。用户通过订单截图或手动录入，为实物建立档案，持续记录购买、持有、维护和处置过程，了解每件物品的真实投入及持有成本。

产品需要回答五个问题：

1. 买了什么，目前处于什么状态。
2. 购入及后续维修、保养、配件累计投入了多少钱。
3. 从购买起已经持有多久。
4. 持有期间的当前日均投入是多少。
5. 出售或淘汰后的实际持有成本和实际日均成本是多少。

典型物品包括手机、电脑、相机、耳机、家电、家具、工具和运动装备。首版围绕具有持续持有周期的实物，不承担日常消费记账、企业财务核算或二手交易撮合。

### 1.2 个人空间与家庭空间

个人空间支持完整的物品管理流程，用户不需要创建或加入家庭即可独立使用。个人物品及记录默认仅自己可见。

家庭空间在相同业务能力上增加共享与协作权限。家庭成员共同维护该空间中的物品；加入家庭不会公开成员的个人空间，也不会自动迁移个人物品。

### 1.3 产品目标

- 降低首次建档成本，允许先记录少量必要信息，再逐步补齐。
- 让每笔投入和每个成本结果都能追溯到真实记录。
- 保留完整生命周期，避免出售或淘汰后丢失历史。
- 在家庭协作中清楚界定可见范围和操作权限。

## 2. 用户与典型场景

| 用户类型 | 主要需求 | 典型场景 |
| --- | --- | --- |
| 个人使用者 | 了解已购物品、累计投入和日均成本 | 导入电脑订单，补记维修费，查看日均投入 |
| 家庭管理者 | 维护共享档案和成员权限 | 建立家庭空间，邀请成员，管理家电和家具 |
| 家庭编辑者 | 共同记录日常使用及维护 | 为洗衣机添加维修支出，补充物品备注 |
| 家庭查看者 | 查看物品信息及家庭投入 | 查询购买凭证和历史支出 |

### 2.1 核心使用场景

- **首次建档**：用户选取一张或多张订单截图，校对识别结果后保存到指定空间。
- **资料不完整**：用户记得物品名称，但暂时找不到金额或日期，先保存档案，后续补充。
- **持续维护**：物品发生维修、保养或配件支出，用户追加记录，累计投入和日均投入相应更新。
- **持续使用**：购入后默认在用，从购买日起连续按日历天数分摊投入，直至出售或淘汰。
- **处置结算**：用户登记出售或淘汰日期、实际回收金额，获得最终实际持有成本。
- **家庭协作**：用户将物品迁入家庭空间，其他成员按角色查看或维护，物品的购买、支出和处置记录连续保留。

## 3. 首版范围

### 3.1 首版必须具备

| 模块 | 首版能力 | 完成标准 |
| --- | --- | --- |
| 物品档案 | 手动新增、截图导入、编辑、资料补充 | 能以少量信息建档，缺失信息不产生虚假的成本结果 |
| 截图校对 | 多图整批识别、多商品表单预填、逐件编辑保存、疑似重复处理 | 用户保存前不自动建立正式档案，不自动合并相似物品 |
| 持续投入 | 维修、保养、配件等支出记录 | 支出可追溯，变更后成本正确更新 |
| 生命周期 | 在用、已出售、已淘汰及事件记录 | 当前持有与已处置可区分，历史连续保留 |
| 价值分析 | 数量、状态、投入及已处置成本 | 统计范围明确，可追溯到对应物品 |
| 空间协作 | 个人空间、创建与加入家庭、角色权限、空间迁移 | 可见范围可解释，个人隐私不因加入家庭而变化 |
| 操作恢复 | 保存反馈、失败重试、删除撤销或恢复 | 失败不会无提示丢失输入，误删有恢复途径 |

### 3.2 暂不纳入首版

- 实时市场价格查询、自动估值及预计残值推荐。
- 维修、换新、出售的情景比较和自动决策建议。
- 二手交易发布、交易撮合、收付款及结算。
- 电商账号自动同步、银行流水或全量消费记账。
- 多币种换算、会计折旧、税务或企业资产核算。
- 同一档案同时属于多个空间或跨空间重复计入统计。

后续若加入预计残值，必须与实际出售收入分别记录、分别解释，不得用于替代本轮的实际成本计算。

## 4. 业务对象与术语

| 对象或术语 | 定义 |
| --- | --- |
| 物品 | 一件具体实物；同一型号的两台电脑应当能够建立两个独立档案 |
| 物品档案 | 实物的基础资料、归属空间、投入、生命周期和相关凭证的集合 |
| 当前持有 | 状态为在用的物品 |
| 已处置 | 状态为已出售或已淘汰的物品 |
| 购入实付 | 用户为该件物品实际支付的购入金额，不等同于包含其他商品的订单总额 |
| 追加支出 | 归属于该物品的维修、保养、配件等实际支出 |
| 累计投入 | 购入实付金额与有效追加支出的合计 |
| 实际回收金额 | 处置该件物品实际收到的金额；零回收与未知回收有不同含义 |
| 实际持有成本 | 物品已处置后，累计投入减去实际回收金额 |
| 导入草稿 | 尚未保存为正式档案的图片识别和校对内容，不参与物品统计 |

一份有效档案在任一时点只归属于一个空间。物品迁移后保留原有身份和历史，来源空间停止统计该档案，目标空间开始统计。

## 5. 功能需求

### 5.1 物品查询与管理

用户能够查看当前空间中的物品，按商品名搜索，并按状态筛选。查询结果必须与当前空间一致，不能混入无权限查看的个人或家庭物品。

当前持有和已处置记录分别可查。用户能够从物品进入完整档案，也能够从价值分析中的状态或指标进入对应物品集合。

空间切换应同步改变物品查询与统计范围。新增时必须明确保存位置，不能仅依赖用户记忆上一次使用的空间。

### 5.2 手动建档与编辑

采用先建档、再补充的方式。首版以名称作为最小建档信息。手动新建默认购买日期为今天，价格留空时按 0 元保存；AI 预填、编辑已有档案和旧草稿中的未知金额、日期保持未知，不套用手动新建默认值。新增物品需明确归属空间，未指定状态时按「在用」建立。

| 字段 | 建档要求 | 业务规则 |
| --- | --- | --- |
| 名称 | 必填 | 用于识别具体物品；可以由识别结果生成，也可以修改 |
| 所属空间 | 必须明确 | 只能保存到用户具有新增权限的空间 |
| 图片 | 可选 | 用于辨认实物；与购买凭证分别管理 |
| 购入实付金额 | 可后补 | 手动新建空价格按 0 元保存；AI、编辑及旧草稿中的未知值保持未知，明确的 0 元与未知分开保存 |
| 购买日期 | 可后补 | 手动新建默认今天，可修改；AI、编辑及旧草稿的未知日期不自动补今天，上传时间不作为识别出的购买日期 |
| 状态 | 需要确定 | 在用、已出售、已淘汰；已处置还需处置信息 |
| 备注 | 可选 | 记录使用说明或其他补充内容 |
| 凭证附件 | 可选 | 订单、发票、维修、配件或处置凭证统一归属物品，可在编辑物品时上传、查看、移除或更换 |

修改购入金额、购买日期或追加支出后，需要重新计算受影响的指标。更正后展示最新有效的业务日期、金额及生命周期记录，不要求保存或展示每次修改的操作者、操作时间和前后差异。

日期、金额输入的合理性应在保存前检查。未来日期、负支出、购买日期晚于处置日期等情况应指出具体问题，保留其他已填写内容。对于确有特殊业务含义的情况，应在评审中确定支持方式，不能静默修正用户数据。

### 5.3 AI 截图导入

识别只使用用户选定截图中实际存在的商品名称、金额、日期等信息；明确的品牌、型号、关键规格合入商品名。用户能够选择单张或多张截图；一张截图可包含多个商品，多张截图也可能对应同一订单或同一物品。

#### 导入过程

1. 用户从当前空间选择一张或多张截图，每批最多 9 张，选图后开始上传与识别。
2. 产品区分上传、排队、识别和失败状态；全部图片上传后整批联合识别。
3. 系统联合理解多张截图，对同订单滚动截图中的重叠商品去重，同款不同订单保留为独立候选。
4. 识别结果预填到与手动添加共用的物品表单；多件通过左右滑动或上一件／下一件切换。
5. 用户修改预填字段、补充未知信息，并处理疑似重复。当前校对页不提供原图、识别说明或历史导入入口。
6. 用户点击「保存物品」确认并保存当前件，保存后自动切换下一件；保存目标为本次进入导入时选定的空间，页面展示其名称。
7. 已保存物品立即进入档案和统计；尚未保存的卡片仅作为当前页面的待处理内容。

#### 识别与校对规则

- 缺失字段保持未知，不编造金额、日期、品牌或型号；截图明确的品牌、型号、规格合入商品名。
- AI 结果只作表单预填，用户检查最终内容并点击保存后才建立档案；不额外要求逐字段确认或数量确认。
- 有明确商品价格就预填：同一商品同时有标价和单件实付时取实付，否则取标价／当前展示价。完整订单明确只有一件商品时，整单实付可作为本件价格；多商品或订单被裁切而归属不明时，不用整单实付覆盖本件标价。
- 不把共用优惠、运费或订单总额自动平均分摊为各件实付。明确多件的订单行拆成多张物品卡片；不把行合计重复填入每件，无法确定单价时金额留空。
- 日期优先取明确购入／下单日期；没有时可用同一商品已取货／已签收日期补填。预计送达、可取货、发货、评价或售后日期不用于补填，年份不全不推测。
- 已取消、已全额退款的订单及其赠品不生成候选；仅某商品行全额退款时只过滤该行。部分退款、退款申请中或「退款／售后」按钮不能当作退款完成。
- 同一件实物可关联多张凭证，但不能因重复截图而自动建立多个有效档案。导入原图不自动成为物品图片或凭证，凭证由用户在物品表单中管理。
- 当前页人工填写内容保留；已有人工修改或保存结果的批次不重新识别，避免覆盖已处理内容。

#### 疑似重复处理

按商品名提示当前用户有权访问的相似档案，匹配结果仅供用户判断。用户可以选择：

- 「同一件，跳过」：不新建物品，不覆盖已有档案。
- 「仍作为新物品」：确认是另一件实物后保存独立档案。
- 暂不保存当前件，继续处理其他卡片；离开页面后按退出规则清空未保存内容。

不得通过重复提示泄露其他成员的个人空间内容。

#### 失败与退出

- 上传失败时保留当前页已完成的上传结果，重试可复用；识别失败按整批重试，不提供逐图识别重试，也不生成空白占位卡片。
- 重新选图会创建新批次，已创建批次的图片集合不再逐图替换、追加或移除。需要手动添加时进入普通物品表单。
- 某件保存失败不影响其他已保存物品。当前件保留输入并允许重试；响应丢失时核实保存状态，重复点击或重试不重复建档。
- AI 选图、上传缓存、校对表单仅保存在当前页面内存，不恢复历史导入任务。切后台保留当前内存，返回时恢复未完成任务查询；系统相册／拍照返回不清空。
- 离开添加页清空未保存内容并尽力取消未完成任务，再次进入需重新选图；已保存物品不受影响。普通手动表单继续使用本机草稿。

### 5.4 物品详情与生命周期记录

物品详情需要提供基础信息、所属空间、当前状态、购入金额、累计投入、持有天数和对应的日均指标，并能查询凭证与补充资料。

生命周期按业务发生日期展示购买、维修、保养、配件购买、其他支出、出售和淘汰。补录以实际购买、支出或处置日期排序，例如 2026 年补录 2025 年购买，记录显示 2025 年的购买日期。更正同一条业务记录时更新原条目，不额外增加「修改资料」事件；当前不展示编辑者、编辑时间或修改前后对比。

有权限的用户可以添加支出、编辑资料、变更状态和登记处置。查看者能够查看同样的业务内容，但不能修改。

### 5.5 追加支出

| 字段 | 要求 |
| --- | --- |
| 所属物品 | 必须明确，支出只能归属于一个物品档案 |
| 类别 | 必填，包含维修、保养、配件和其他 |
| 金额 | 必填，记录本次实际支付金额 |
| 日期 | 必填，记录费用实际发生日期 |
| 备注 | 可选 |
| 凭证管理 | 统一在所属物品的编辑页上传、更换或移除，不要求在支出表单中单独上传或逐笔绑定 |

保存后立即更新该物品的累计投入和相关成本。支出更正同步修正原支出条目、生命周期展示和统计，避免一笔费用被重复计算；不另生成更正操作记录。

首版以用户记录的真实支出为准，不推测维修市场价。配件若作为某物品的追加支出计入，不应再把同一笔支付自动计入另一个独立档案；产品应帮助用户明确费用归属。

### 5.6 状态与处置

新建物品默认「在用」，购买后视为持续使用，按日历天数计算。取消闲置状态、闲置筛选、闲置统计和使用状态切换入口；保留出售与淘汰。旧版闲置档案自动转为在用（包括回收站内档案），购买日期、金额、支出和历史记录保持不变，不重置计时。

| 状态变化 | 业务结果 |
| --- | --- |
| 在用 → 已出售 | 登记实际处置日期和回收金额，转入历史处置记录 |
| 在用 → 已淘汰 | 同样登记处置日期和实际回收，零回收需要明确确认 |

出售和淘汰都保留档案、凭证和投入记录，不等同于删除。处置日期确定后，实际持有天数不再随当前日期增长。

处置需填写实际回收金额；不知道金额时不能用 0 替代，可以暂不完成登记并保留待处理内容。输入 0 时需明确确认「本次没有收到回收款」。

购买日期或购入金额仍缺失的物品可以保留档案及已确认的处置信息，但相关成本显示「待补充」。已经知道处置日期和回收金额，不代表其他缺失数据可以视为 0。

误填的处置日期或金额应允许有权限的用户更正，并更新原处置条目。处置后补录处置前发生的真实支出，也会重新计算最终成本；「最终」表示不随时间自然增长，不表示错误数据无法修正。真实发生的退货、出售后买回等额外业务不在首版范围内，不能当作普通状态切换处理。

### 5.7 删除与恢复

删除用于移除不再需要的档案，和出售、淘汰分开处理。当前通过回收站恢复误删档案，不自动到期清除；恢复保留原有物品身份、资料、支出和生命周期记录。

待删除档案不参与有效物品统计，恢复后重新计入一次。若原空间已经不可用或操作者失去权限，不得绕过权限恢复到该空间，应说明无法恢复的原因和可行的下一步。

当前不提供永久删除。未来若设置恢复期限或永久删除，需另行确认规则并说明不可恢复的后果；原型中的 30 天不作为当前政策。

### 5.8 价值分析

价值分析以当前空间为范围，统计数量、状态分布、购入及追加投入和已处置实际成本。每项结果必须能追溯到参与统计的物品。

| 指标 | 统计口径 |
| --- | --- |
| 物品数量 | 范围内有效档案数；排除导入草稿和待删除档案 |
| 状态分布 | 按在用、已出售、已淘汰分别计数 |
| 购入投入 | 范围内物品已确认的购入实付合计 |
| 追加投入 | 同一批物品的有效追加支出合计 |
| 累计投入 | 完整物品的购入及追加投入；存在缺失时需明确统计不完整 |
| 当前日均投入（空间首页） | 当前空间内在用物品各自当前日均投入之和；不计已处置、导入草稿、待删除档案 |
| 已处置实际成本 | 已处置物品的累计投入减去实际回收；数据缺失者单独标识 |

#### 时间与范围说明

- 数量和状态分布要说明是当前状态快照及其统计日期。
- 当前持有物品的历史投入按各物品购买以来的记录计算，不能被误读为本月支出。
- 当前按物品状态筛选，不提供处置日期区间筛选。已处置实际成本包含对应物品整个持有期间的投入。
- 空间首页按 Figma 设计展示「当前日均投入」，计算当前空间内每件当前持有物品的日均投入后求和，不使用统一持有天数作分母，也不取平均。
- 该指标描述当前持有物品各自历史投入的每日分摊合计，不代表当天现金支出。所有在用物品均参与；已出售、已淘汰、导入草稿及待删除档案不参与。
- 有当前持有物品缺少购入金额或购买日期时，只汇总可计算的部分，标题改为「已知日均投入」，并展示待补充件数。若全部缺失，显示「待补充」；没有当前持有物品时显示 0.00 元/天。
- 空间切换、资料更正、追加支出、状态与处置变化、删除恢复和迁移后，首页日均指标与明细同步更新；可通过指标进入参与统计的当前持有物品集合。

存在缺失金额时，可以展示「已知投入」及未完整记录的物品数量，但不能把它标为完整的累计投入。

## 6. 成本计算规则

### 6.1 公式

```text
累计投入 = 购入实付金额 + 有效追加支出合计

当前持有天数 = 统计日期与购买日期的日历日期差 + 1
当前日均投入 = 累计投入 ÷ 当前持有天数

实际持有天数 = 处置日期与购买日期的日历日期差 + 1
实际持有成本 = 累计投入 − 实际回收金额
实际日均成本 = 实际持有成本 ÷ 实际持有天数

空间当前日均投入 = Σ（当前空间内每件在用物品的累计投入 ÷ 该物品当前持有天数）
```

### 6.2 统一规则

1. 日期差按日历天数计算，包含购买当天，最少按 1 天计算；无效日期顺序不能靠「最少 1 天」掩盖。
2. 从购买日期开始持有，不能从录入、导入或加入家庭的日期开始计时。
3. 购入后默认持续使用，每个日历日均计入持有天数，不提供暂停计时或按使用次数计费。
4. 处置后以处置日期作为终点，不随查看日期继续增长。
5. 已保存档案中的未知金额、购买日期、处置日期或回收信息，对应指标显示待补充。手动新建的空价格按第 5.2 节默认值保存为 0；该入口规则不改变 AI、已有档案和旧草稿的未知值语义。
6. 没有追加支出记录时，其追加支出合计为 0；这不代表未知的购入实付也为 0。
7. 日均投入用于解释成本摊薄，不代表物品的全部使用价值，也不是使用频率。
8. 首版默认人民币；单笔金额按分记录，日均结果按两位小数展示，中间计算不逐步舍入。

业务日期按 UTC+8 日历日期统计，购买当天计入；回收金额高于累计投入时，允许实际持有成本为负，不静默归零。

### 6.3 缺失值处理

| 情况 | 可以展示 | 不能计算或宣称 |
| --- | --- | --- |
| 已知金额，缺购买日期 | 已确认投入 | 持有天数与日均投入 |
| 已知购买日期，缺购入金额 | 持有天数、已知追加支出 | 完整累计投入与日均投入 |
| 已处置但购入资料缺失 | 处置日期、已确认回收金额、已知支出 | 完整实际持有成本或实际日均成本 |
| 回收金额未知 | 已确认的其他记录 | 把未知回收当作 0 得出最终成本 |
| 用户明确确认零回收 | 按 0 元回收计算 | 把零回收误标为待补充 |

### 6.4 校验样例

以下示例统一以 **2026-10-19** 为统计日期。

| 样例 | 购入日期 | 截止或处置日期 | 天数 | 投入与回收 | 结果 |
| --- | --- | --- | ---: | --- | --- |
| 电脑购入后 | 2025-06-07 | 2026-10-19 | 500 | 购入 8,000 元 | 当前日均投入 16.00 元 |
| 电脑维修后 | 2025-06-07 | 2026-10-19 | 500 | 购入 8,000 元，维修 500 元 | 当前日均投入 17.00 元 |
| 电脑出售后 | 2025-06-07 | 2026-10-19 | 500 | 累计投入 8,500 元，实际回收 3,000 元 | 实际持有成本 5,500 元，实际日均成本 11.00 元 |
| 在用耳机 | 2024-10-20 | 2026-10-19 | 730 | 累计投入 3,000 元 | 当前日均投入 4.11 元 |
| 已出售相机 | 2024-10-20 | 2025-10-19 | 365 | 累计投入 5,000 元，回收 3,000 元 | 实际日均成本 5.48 元，后续日期不改变结果 |

## 7. 空间与协作

### 7.1 创建与加入家庭

创建家庭的用户成为管理者，可以邀请其他用户。创建或加入时填写家庭内昵称，成员可修改自己的昵称，各家庭独立。邀请有效期为 7 天，可供多人使用，默认角色为编辑者，也可选择查看者。受邀者需了解目标家庭和加入角色并主动同意；仅收到邀请或打开邀请不能自动成为成员。

邀请者先选择编辑者或查看者，再生成邀请；弹窗展示家庭名称、角色、微信小程序码、有效期和“分享给好友”按钮。产品界面不显示邀请码、复制、手动输入、历史邀请列表或撤销入口；后台接口保留兼容。每次明确生成创建新邀请，旧邀请仍按原期限有效。

受邀者通过分享或微信扫码直接打开家庭邀请卡片，自动加载家庭信息，不再手动查看邀请。有效期按设备本地时区显示中文日期与时间，并标注剩余天数、小时数；不足一小时单独提示。填写家庭昵称并确认后才加入；已有成员直接进入家庭。无参数、加载、网络错误和邀请失效均有独立状态。分享卡片使用专门的用本家庭邀请封面。

加入家庭只授予该家庭空间的权限，不公开或迁移任何个人档案。邀请失效、撤销、已加入等情况应有明确结果，重复接受邀请不能产生重复成员关系或覆盖已有角色、昵称。被移除成员须使用移除后新生成的邀请重新加入，旧邀请对其他用户仍按原有效期生效。

### 7.2 角色权限

以下为当前首版角色分工。家庭物品外迁和永久删除暂不开放，未来扩展时另行确认规则。

| 操作 | 管理者 | 编辑者 | 查看者 |
| --- | :---: | :---: | :---: |
| 查看家庭档案、凭证、历史和统计 | 是 | 是 | 是 |
| 新增和编辑物品 | 是 | 是 | 否 |
| 添加或更正支出 | 是 | 是 | 否 |
| 登记或更正处置 | 是 | 是 | 否 |
| 可恢复删除及恢复 | 是 | 是 | 否 |
| 邀请、移除成员和调整角色 | 是 | 否 | 否 |
| 将个人物品迁入家庭 | 本人有权且目标可新增 | 本人有权且目标可新增 | 否 |
| 将家庭物品迁出 | 暂不开放 | 暂不开放 | 否 |

个人空间由本人独立管理。家庭角色不授予访问其他成员个人空间的权限。当前仅管理者可调整或移除其他非管理者成员，不提供自行退出、管理者转交、家庭解散或管理者角色调整；成员均可修改本人的家庭昵称。

成员被移除或权限降低后，后续操作应按新权限执行。已经开始编辑但尚未保存的内容，不能因为曾经有权限而继续写入；应保留用户可保留的输入并说明原因，不泄露已失去访问权的资料。

### 7.3 空间迁移

迁移前，用户需知道来源空间、目标空间、迁移后谁能查看或修改，以及历史和凭证是否会随档案可见。

迁移应满足以下业务结果：

- 来源与目标的相应操作权限均满足要求。
- 同一物品只有一份有效档案，不复制成两个并同时统计。
- 购买、支出、处置和物品凭证保留，生命周期记录连续。
- 迁移失败时保持原归属，不出现两个空间都无记录或同时持有副本的中间结果。
- 迁移成功后，当前统计按新归属更新；既往事件不因迁移被改写。

从家庭迁出会让原成员失去对共享物品的访问，涉及共享资料归属，不能直接沿用个人物品迁入的默认授权。首版最终规则需单独确定。

### 7.4 生命周期记录边界

记录页和详情页展示物品随时间发生的业务事件：购买、维修、保养、配件购买、其他支出、出售、淘汰。每条记录展示业务日期、类别、金额及适用的备注；同一业务记录更正后展示最新内容，避免重复计入事件或费用。

不要求记录或展示「谁在何时改了什么」，也不要求物品编辑、迁移、删除恢复或成员角色变更的操作审计页面。后端已有的事件存储可保留用于内部处理，不作为首版面向用户的功能或验收缺口。

当前实现已取消闲置状态及其切换入口，首版不新增闲置事件；旧闲置数据按第 5.6 节转为在用。成员离开家庭不删除物品已有的业务记录。

## 8. 主要业务流程

### 8.1 从截图到最终成本

```text
选择截图
  → 上传并识别
  → 逐件校对商品名 金额 日期
  → 处理疑似重复或缺失信息
  → 确认目标空间并保存
  → 查看持有期间日均投入
  → 添加维修支出并更新累计投入
  → 登记出售日期和实际回收金额
  → 查看固定的实际持有天数与实际日均成本
```

分支要求：无重复结果直接继续；同一件实物可以跳过新建；金额或购买日期缺失可以先建档；识别失败可改手动；没有回收必须明确确认零元。

### 8.2 家庭协作

家庭成员面板使用深绿渐变家庭标题和简洁成员列表。管理者在前，同角色本人优先，其他成员按加入时间倒序；分页前保证排序。本人标记“我”，昵称修改按需打开独立弹窗。只有管理者可以调整其他非管理者的权限或移除成员，操作前确认；编辑者与查看者仅能修改自己的家庭昵称。


```text
创建家庭 → 发出邀请 → 受邀者主动加入 → 按角色查看或维护
个人物品 → 确认可见范围变化 → 迁入家庭 → 历史保留并更新统计
成员记录购买／支出／处置 → 更新物品生命周期和成本 → 其他有权限成员可查
```

### 8.3 误删恢复

```text
删除档案 → 暂停计入统计 → 在回收站恢复
  → 校验当前恢复权限 → 恢复原档案及历史 → 重新计入一次
```

## 9. 异常与边界处理

| 情况 | 产品行为 |
| --- | --- |
| 首次使用无物品 | 可以直接新增或导入，不要求先创建家庭 |
| 金额或日期未知 | AI、编辑及旧草稿保留未知，相关成本待补充；手动新建默认今天、空价格按 0 元保存 |
| 上传或识别中 | 说明正在进行的阶段，不提前声称已保存 |
| 整批截图识别失败 | 允许整批重试、重新选图开始新批次，或进入普通手动表单；不生成占位物品 |
| 单件实付与总额无法区分 | 暂不确认金额，由用户核对 |
| 相同商品名或重复截图 | 提示核对，不自动合并或覆盖 |
| 多件物品中某件保存失败 | 当前件保留输入并提示重试，其他已保存物品不受影响，不重复建档 |
| 提交时失去编辑权限 | 不保存无权变更，解释权限变化，避免输入无提示丢失 |
| 多人同时修改同一记录 | 提示记录已经变化，避免后保存者无提示覆盖前一人的修改 |
| 回收金额为空或为 0 | 空值不能作为零元；零元需明确确认 |
| 同一天购买并处置 | 持有 1 天，不出现除以 0 |
| 后续查看已处置物品 | 天数和结果不随查看日期变化 |
| 修正业务金额或日期 | 更新原生命周期条目并重新计算关联指标，不新增修改操作记录 |
| 保存失败或网络中断 | 保留可恢复的输入，说明未保存，允许重试 |
| 误删物品 | 通过回收站恢复；当前不提供永久删除 |

## 10. 数据与服务质量要求

### 10.1 真实数据与一致性

同一物品详情、列表和分析中的金额、状态、空间归属必须一致。用户完成追加支出、处置、更正或迁移后，受影响的结果应同步更新，不能继续显示未标识的旧结果。

操作需要有明确的成功或失败结果。重复请求不能产生重复档案、重复支出或重复处置。多人协作发生冲突时，优先保护已保存的数据并让用户知道差异。

### 10.2 隐私与使用授权

只处理用户主动选择的图片。识别前需要说明图片是否上传、用于什么目的；截图可能含姓名、地址、订单号等信息，应支持用户在提交前移除不必要内容。

个人与家庭空间分别按权限控制访问。日志、分析和重复提示也必须遵守相同权限边界。云端图片保留期、是否用于模型训练及删除机制未确定前，不作已具备的承诺，须在上线前明确。

### 10.3 使用可靠性

首版需验证 iOS 和 Android 微信中的核心任务，包括输入、授权、返回、网络中断后的恢复。用户放大文字、使用读屏或减少动态效果时，仍应能够完成建档、校对、支出和处置等主要任务；具体样式不在本 PRD 内定义。

上传容量、单次图片数量、识别等待时间和数据规模上限应在实现评估后明确。上线前需针对约定上限和弱网情况验收，不把未经验证的性能数字写作服务承诺。

## 11. 产品效果评估

首版可通过以下指标评估是否降低录入成本并形成持续记录。指标仅定义口径，目标值待试用基线形成后确定，不代表当前已有数据。

| 指标 | 定义 |
| --- | --- |
| 首次建档完成率 | 首次启动建档的用户中，完成至少一个有效档案保存的比例 |
| 截图导入完成率 | 发起识别的批次中，至少保存一个档案或明确关联到已有实物的比例 |
| 关键字段修正率 | 用户确认的识别字段中，金额、日期等被修改的比例；按字段分别统计 |
| 资料完整率 | 有效档案中同时具备购入实付和购买日期的比例 |
| 持续记录比例 | 在约定观察期内，除建档外又追加支出或生命周期记录的用户比例 |
| 处置结算完整率 | 已登记处置的档案中，具备完整投入、购买日期、处置日期和回收信息的比例 |

统计产品使用行为时，不采集无关的订单原文、私人备注或图片内容。观察期、样本定义和目标值需在评审中统一。

| 编号 | 场景与操作 | 预期结果 |

| AC02 | 手动新建只填名称；另检查 AI、编辑和旧草稿中的未知值 | 手动新建空价格按 0 元、默认今天保存；其他入口未知值仍保持未知，对应指标待补充 |
| AC03 | 录入电脑 8,000 元及 2025-06-07 | 在 2026-10-19 持有 500 天，当前日均投入 16.00 元 |

| AC06 | 电脑于 2026-10-19 以 3,000 元出售 | 实际成本 5,500 元，实际持有 500 天，实际日均成本 11.00 元 |

| AC14 | 加入家庭后查看个人空间 | 个人物品仍仅本人可见，家庭成员不能通过搜索或重复提示获取 |
| AC15 | 查看者尝试修改物品或支出 | 修改不生效；无论通过何种入口均不能越权 |
| AC16 | 将个人物品迁入可编辑家庭 | 一份有效档案归入目标空间，来源停止统计，历史和凭证保留 |
| AC17 | 迁移或保存过程中权限发生变化 | 不绕过新权限；失败后不会产生重复或丢失的有效档案 |
| AC18 | 两名成员修改同一条记录 | 后提交者能得知冲突，不无提示覆盖已保存结果 |
| AC19 | 删除后恢复档案 | 原资料与历史恢复，统计只计入一次 |
| AC20 | 分析范围存在购入金额缺失的物品 | 标明已知投入和不完整件数，不宣称总投入完整 |
| AC22 | 更正一笔维修金额或日期 | 原维修条目更新，生命周期中只显示一条有效维修记录，关联累计投入和最终成本重新计算 |
| AC23 | 当前空间包含日均 16 元的在用电脑、日均约 4.109589 元的在用耳机及一件已出售相机 | 首页当前日均投入为 20.11 元/天，已出售相机不参与；先以未舍入值求和，再显示两位小数 |
| AC24 | 当前持有集合存在金额或购买日期缺失 | 首页改为「已知日均投入」并标明待补充件数；全部缺失时显示「待补充」，空集合显示 0.00 元/天 |
| AC25 | 读取旧版包含闲置档案的数据并再次读取 | 自动转为在用且只迁移一次，保留原购买日期、投入、历史和删除标记，日均计算连续 |
| AC26 | 在编辑物品中上传、更换或移除维修／配件凭证 | 凭证归属该物品，在详情可查看；不要求在支出表单中单独上传或绑定 |
| AC27 | 查看购买、维修、配件购买和出售记录，再更正业务信息 | 按业务日期展示有效事件，不显示编辑者、修改时间或修改前后差异，不产生重复业务记录 |
| AC28 | AI 校对期间切后台，再返回；随后离开页面重新进入 | 切后台保留当前内容，离开后清空未保存内容；已保存物品保留，再次进入需重新选图 |
| AC29 | 创建家庭、多人接受邀请、移除后尝试旧邀请 | 邀请 7 天有效、默认编辑者；重复接受不改变昵称或角色，被移除者必须使用新生成邀请 |

## 13. 待确认事项与依赖

### 13.1 当前边界与待确认政策

已确认并按当前实现执行：

- 手动新建默认今天、空价格保存为 0；AI、编辑和旧草稿保留未知值。
- 记录物品生命周期，不要求操作审计；不提供处置日期区间筛选，凭证统一在物品表单中管理。
- 邀请 7 天内多人可用，默认编辑者，可改选查看者；被移除成员须使用新邀请重新加入。
- 回收站不自动到期、不提供永久删除；家庭退出、转交、解散及家庭物品迁出暂不开放。
- 业务日期统一 UTC+8；实际成本允许负值。购买、支出及处置日期不能晚于今天；有购买／处置日期时，支出不能早于购买或晚于处置。
- AI 最多每批 9 张，整批识别与重试；切后台保留、离开页面清空，不恢复历史导入。普通表单保留本机草稿。

仍需在扩展或上线前明确：

| 事项 | 当前边界或待确认问题 | 确认时点 |
| --- | --- | --- |
| 正式产品名称 | 当前界面使用「用本」，正式对外名称待确认 | 对外发布前 |
| 删除恢复政策 | 当前可恢复且不自动到期；若增加期限或永久删除，需另行确定 | 扩展删除功能前 |
| 家庭管理扩展 | 退出、管理者转交、解散、家庭物品迁出当前不开放；规则待扩展时确认 | 扩展家庭功能前 |
| 部分回款和处置费用 | 当前只登记一笔已确认回收；分期与手续费不单独建模 | 扩展处置功能前 |
| 数据保留与隐私 | 云端截图、未提交任务、物品凭证和孤立文件的保留／删除政策，以及模型训练用途说明 | 对外发布前 |
| 容量与服务承诺 | 当前已有上传与识别限制；上线前验证适用设备、数据规模和弱网边界，不承诺未验证的性能 | 对外发布前 |
